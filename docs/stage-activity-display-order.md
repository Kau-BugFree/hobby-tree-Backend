# API-24 정식 노출 순서·복합 커서

> 2026-11-19 통합 계약: [활동 APIv2](api-v2-activities.md) · [코드·명세 대조/후속](activity-contract-status.md). 구현·병합과 운영 반영 상태는 구분한다.

Issue #118. APIv2.md의 API-24와 2026-11-19 사용자 선택을 기준으로 한다.
기준 develop은 ff6e729이며 운영 적용 결과를 의미하지 않는다.

## 확정 정책

- activities.display_order: nullable INTEGER, 0~2147483647. 기본값/기존 행은 NULL이며 임의 순번을 백필하지 않는다.
- 단계 안에서 display_order ASC NULLS LAST, activity_id ASC. 동순위는 허용하고 ID로 안정적으로 구분한다.
- 모든 기존 값이 NULL인 상태에서는 종전 ID 오름차순을 그대로 유지한다. 명시한 순위는 미지정 활동보다 먼저 나온다.
- API 경로·응답 필드·size 기본20/최대50·공개 활동 필터·본인 저장 여부·잠긴 단계 미리보기는 유지한다.
- displayOrder는 서버 내부 편집 메타데이터이며 이번에 응답 필드나 편집 API를 추가하지 않는다.
- 썸네일은 활동→취미→null, 비용·시간·난이도 등의 null 의미는 API-25 및 #127 계약을 유지한다.

## 조회·커서

DB에서 공개 활동을 먼저 제한하고 복합 키 조건·정렬·size+1을 적용한다. 메모리 전체 정렬이나 OFFSET을 사용하지 않는다.
서명된 api24-order-v2는 사용자·단계·displayOrder(또는 null)·activityId에 묶이고 전용 파생 키를 사용한다.
0순위와 미지정은 구분하며 정규 표현이 아닌 숫자·범위 초과·위조·다른 사용자/단계/API 커서는 COMMON400_1이다.

이전 api24-id-v1은 정확한 기존 서명이 있어도 COMMON400_1로 거절한다. FE는 커서를 해석/변환하지 않고
첫 페이지로 돌아가 다시 조회한다. 버전 전환 직후 무한 재시도하지 않는다. 이번 정책은 사용자가 명시적으로 선택했다.

커서에 당시 정렬 값을 담아 anchor가 삭제·비공개·다른 단계로 이동해도 그 행을 다시 조회하지 않는다.
한 응답은 REPEATABLE_READ 스냅샷이지만 여러 HTTP 페이지를 같은 DB 스냅샷으로 고정하지는 않는다.
페이지 사이에 다른 활동의 순위·공개 여부·소속이 바뀌면 앞뒤로 이동한 항목의 누락/재등장이 가능하다.
카탈로그 편집 후 전체 최신 순서가 필요하면 첫 페이지부터 다시 조회한다.

## V32와 콘텐츠 편집

기존 V1~V31은 수정하지 않는다. V32는 nullable 열·비음수 CHECK·공개 활동 전용
(hobby_stage_id, display_order, activity_id) 인덱스만 추가한다. 기존 제목·시각·콘텐츠 버전·저장·기록·성장 원장을 갱신하지 않는다.
초기/후속 INSERT의 미지정 순위도 NULL이며, 명시적인 0을 미지정으로 바꾸지 않는다.

순위는 실행 콘텐츠가 아니므로 기존 V18 규칙에 따라 순위만 편집해도 content_version/content_updated_at은 바뀌지 않는다.
시작 스냅샷·체크·완료 조건도 바뀌지 않는다. 승인된 콘텐츠 writer의 권한·잠금 순서·트랜잭션 규약은 #130에서 관리한다.
편집자는 같은 단계의 여러 순위를 한 트랜잭션으로 변경하고, 다른 내용도 수정하면 기존 버전 규칙을 그대로 적용한다.
관리 편집 API·실제 콘텐츠 순위 부여·운영 SQL 실행·이미지 저장소/업로드는 이번 구현에 포함하지 않는다.

## 향후 배포·복구 검토

- 설치 전 실제 develop 및 열린 PR의 migration 번호를 다시 확인한다. 이번 검증은 V32가 비어 있는 상태에서 시작했다.
- 실제 적용 전 스냅샷·DDL 시간/잠금·DB 여유 공간을 점검하고 승인받는다. 일반 CREATE INDEX는 쓰기를 잠글 수 있다.
- DB V32 적용 뒤 새 앱 전체로 교체하고 공개한다. 구·신 앱을 섞어 커서 형식이 요청마다 바뀌게 하지 않는다.
- V32 적용 전 구 앱은 신규 nullable 열을 몰라도 기존 ID 조회가 가능하다. V32 적용 후 구 이미지 복구도 데이터 손실을 요구하지 않는다.
- 구 이미지 복구 시 API-24는 다시 ID 정렬이며 v2 커서를 읽을 수 없다. 첫 페이지 초기화와 순위 노출 일시 중단을 함께 안내한다.
- V32 적용 실패는 트랜잭션 전체 rollback이며 적용 이력과 열·제약이 부분 적용되지 않음을 격리 환경에서 검사한다.
  적용된 migration 삭제/수정, 순위 값 제거, 스냅샷·성장 이력 재작성은 복구 수단으로 사용하지 않는다.
